# State model

**You own the rules of a flow that moves between states: each holds on every path or has a replayed bug path.** Use it when a change touches a flow with more than one actor, or with retries, restarts, or timeouts, such as a job lifecycle, a handoff, a deploy gate, or a protocol ([**Model the domain**](../../anchorloop/principles/model-the-domain.md)).

1. Align: name the reader (the person who decides whether the behavior is right), the actors, and the rules in the reader's own sentences, such as "a paid order is never lost". A rule the reader has not agreed to is a question for them, not a rule. For each actor, name where its steps come from: code, a prompt, the words of a refusal, a person's habit; a step an agent would have to improvise stays out of the model and goes in the reply. Find the project's test rig for these components now, and name the model's steps after what it can drive.
2. Spec: write a TLA+ spec, its configs, and the view module. A flow that outlives this change (a lifecycle, a protocol, a gate others build on) keeps them beside its code under version control, with each check's `chart.mmd` and `report.md` but not `tlc.out`, so the next change to the flow edits the model first and reruns the check in seconds; a one-off investigation keeps them in a scratch folder. Keep two configs: a small one that draws whole (one of everything, no failure steps), which is the chart the reader confirms, and the full one for the check, since the chart budget counts model states.
   - Give each agreed rule an `INVARIANT`, adding the variable it needs; a rule that fails is a finding and stays as written. When the project's own documents accept the behavior, quote them beside the finding, and the reader chooses between rule and document.
   - A rule that something always ends a certain way becomes: in every state where no actor still has a step for it, the outcome holds. Write "an actor still has a step" as its own definition; it lists what you assume each actor does. When stopping anywhere is fine, set `CHECK_DEADLOCK FALSE`.
   - Model the steps that interleave, including the failing ones (a retry, a restart, a timeout, a second actor). One step is one thing another actor can come between; two real steps joined into one go under what the model leaves out. Keep the constants small.
3. Check: read the `statechart` skill's `SKILL.md` and run it with a view module that turns each state and step into the reader's words. `statechart` is a separate user skill that the user's root installs and anchorloop does not ship; its frontmatter keeps it out of the skill list, so read it by path, usually `~/.agents/skills/statechart/SKILL.md`, and run `~/.agents/skills/statechart/scripts/statechart SPEC.tla --config FILE --view view.mjs --out DIR` (it refuses a non-empty `DIR`: remove it first). When it is absent, say so and stop at the spec.
   - The report gives one path per broken rule, the shortest, and it can hide other causes: switch that cause off (a constant at 0, or the fix modeled in a scratch copy) and rerun until the rule holds; each run's path is one more cause.
   - For each rule that holds, change the spec once the way wrong code would behave and watch the rule break; a rule no change breaks was not checked.
   - After the first report, read every step against the code once more, and for each flag that makes a rule true, check where it is cleared.
4. Replay: turn each violating path into a test on the real code and run it red for the modeled reason ([**Sequence verifiable units**](../../anchorloop/principles/sequence-verifiable-units.md)). Assert the rule at the end of the path in the reader's words; a step a fix may refuse is an attempt whose refusal the test allows, and a step that is an agent's or a person's move is a comment in the test and an assumption in the reply. A path that does not reproduce means the model is wrong until you show otherwise: correct the model, or record why the code differs.
5. Show: write the small config's chart, each rule with its result, and each path with its red output into a markdown page, and open it with `show_doc` and `view: "page"`; the reader confirms the flow and the rules before any production change, and a correction reruns step 3.
6. Act: fix until each replay test is green, update the spec to describe the fixed behavior, and rerun the check until every rule holds. When fixes are out of scope, the replay tests stay red on an unmerged branch (or marked expected-to-fail the way the project's runner allows), each named in a ticket.

**Anchor:** the TLC report, where every rule holds and was shown able to break, or each broken rule has a replay test run red for the modeled reason, then green after the fix or parked in a ticket when fixes are out of scope.

**Reply:** the rules, each bug path with the reader's sentence for it, what the model leaves out (joined steps, improvised agent moves), and the command that reruns the check.
