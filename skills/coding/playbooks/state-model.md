# State model

**You own the rules of a flow that moves between states: each holds on every path or has a replayed bug path.** Use it when a change touches a flow with more than one actor, or with retries, restarts, or timeouts, such as a job lifecycle, a handoff, a deploy gate, or a protocol ([**Model the domain**](../../anchorloop/principles/model-the-domain.md)).

1. Align: name the reader (the person who decides whether the behavior is right), the actors, and the rules in the reader's own sentences, such as "a paid order is never lost". A rule the reader has not agreed to is a question for them, not a rule; with no reader present, a rule the code already enforces in the plain sequential case counts as agreed and the rest are marked proposed, checked and shown with their paths. A decision given in words that reads two ways on a rule: model the reading the existing code gives, make the other a constant, and ask. For each actor, name where its steps come from: code, a prompt, the words of a refusal, a person's habit; a step an agent would have to improvise stays out of the model and goes in the reply, and a step whose outcome a model or classifier decides is modeled as its possible outcomes only when a rule is about them. Find the project's test rig for these components now, and name the model's steps after what it can drive. When the rig replays a path in seconds, drive each path you already suspect once before the spec, reusing earlier scratch probes: a step the code does not tell apart is not a step of the model.
2. Spec: write a TLA+ spec, its configs, and the view module. A flow that outlives this change (a lifecycle, a protocol, a gate others build on) keeps them beside its code under version control (this location wins over the `statechart` skill's "scratch folder outside the repo"), in the folder that holds the project's long-lived flow contracts, with a README table of each config's result; a one-off investigation keeps them in a scratch folder. Commit the `chart.mmd` and `report.md` of the small and the family checks, a result line for each other config, and no `tlc.out`, so the next change edits the model first. Keep a small config that draws whole (one of everything, no failure steps), which is the chart the reader confirms, and the configs for the check, sized and split as [state-model-checks](../references/state-model-checks.md) says, since the chart budget counts model states. Configs that differ only in constants come from one script, which also reruns them all. Answer the loop's reach notice for a model beside the code with: a model and its reports, no production file.
   - Give each agreed rule an `INVARIANT`, adding the variable it needs; a rule that fails is a finding and stays as written. A rule about what an actor emitted (a message, a notice) reads a variable holding the last step's emitted value, as do the labels. When the project's own documents accept the behavior, quote them beside the finding, and the reader chooses between rule and document.
   - A rule that something always ends a certain way becomes: in every state where no actor still has a step for it, the outcome holds. Write "an actor still has a step" as its own definition; it lists what you assume each actor does, and TLC checks only where it is reachable. When stopping anywhere is fine, set `CHECK_DEADLOCK FALSE`.
   - Model the steps that interleave, including the failing ones (a retry, a restart, a timeout, a second actor). One step is one thing another actor can come between; two real steps joined into one go under what the model leaves out. Keep the constants small.
   - Write each guard and suspected cause as a BOOLEAN constant, so switching it off is a config edit that stays beside the code. A decided design not yet built (fixes agreed in words) is a constant `Design` (`today`, `decided`) and a set `Fixes` of proposed changes, so one spec checks the code as it is and the design.
3. Check: read the `statechart` skill's `SKILL.md` and run it with a view module that turns each state and step into the reader's words. `statechart` is a separate user skill that the user's root installs and anchorloop does not ship; its frontmatter keeps it out of the skill list, so read it by path, usually `~/.agents/skills/statechart/SKILL.md`, and run `~/.agents/skills/statechart/scripts/statechart SPEC.tla --config FILE --view view.mjs --out DIR`; the command exits 1 when a rule breaks and still writes the report, so a rerun script must not stop on it; it refuses a non-empty `DIR` (remove it first), and [state-model-checks](../references/state-model-checks.md) lists its other refusals. When it is absent, say so and stop at the spec.
   - The report gives one path per broken rule, the shortest, and it can hide other causes: switch that cause off (its constant at false, or the fix modeled in a scratch copy) and rerun until the rule holds; each run's path is one more cause.
   - A rule that breaks in the small config is a finding in the flow the reader thought plain: show it first, on the chart.
   - For each rule that holds, change the spec once the way wrong code would behave, in a config that exercises the rule, and watch it break; a rule no change breaks was not checked. When the change breaks nothing, a second guard holds the rule: find it and make both constants.
   - With a design modeled, run `Fixes` whole, then each fix left out (`without/Pn`): a fix whose removal breaks nothing is not needed. A rule that breaks under the decided design is a gap in it: add the smallest change as one more `Fixes` entry, and replay only today's code. Two rules that cannot both hold go on the page with each path, and the reader chooses.
   - After the first report, read every step against the code once more, and for each flag that makes a rule true, check where it starts and where it is cleared.
4. Replay: turn each violating path into a test on the real code and run it red for the modeled reason ([**Sequence verifiable units**](../../anchorloop/principles/sequence-verifiable-units.md)). Assert the rule at the end of the path in the reader's words; a step a fix may refuse is an attempt whose refusal the test allows, and a step that is an agent's or a person's move is a comment in the test and an assumption in the reply. Replay an interleaving by pausing one request at the step boundary the model names; when the rig lacks a guard the path depends on, say what the test emulated and name the rig that would not need it. A green control test per race (the same steps, no interleaving) shows the red is for the modeled reason. For an always-ends rule, try every route the actor has and quote each refusal. A break the project's documents accept needs no new red test: the quote and the existing test that pins it anchor it. A path that does not reproduce means the model is wrong until you show otherwise: correct the model, or record why the code differs.
5. Show: write the small config's chart, each rule with its result, and each path with its red output into a markdown page in the reader's language and business words, and open it with `show_doc` and `view: "page"`; the reader confirms the flow and the rules before any production change, and a correction to a rule goes back to step 2 and invalidates the replays of step 4. When the work started from reported symptoms, the page maps each to the paths that produce it, or says it was not reproduced or lies outside the model.
6. Act: fix until each replay test is green, update the spec to describe the fixed behavior, and rerun the check until every rule holds. When fixes are out of scope, the replay tests stay red on an unmerged branch (or marked expected-to-fail the way the project's runner allows), one ticket per bug naming its test.

**Anchor:** the TLC report, where every rule holds and was shown able to break, or each broken rule has a replay test run red for the modeled reason, then green after the fix or parked in a ticket when fixes are out of scope.

**Reply:** the rules, each bug path with the reader's sentence for it, what the model leaves out (joined steps, improvised agent moves), and the command that reruns each config (or the one script that reruns them all).
